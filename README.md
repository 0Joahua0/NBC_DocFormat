## 项目简介

NBC_DocFormat 用于处理 `.docx` 公文材料中的常见格式问题，包括标题层级、字体字号、段落缩进、行距、标点和表格格式。所有处理均在本地完成，不上传、不收集文档内容。

## 核心能力

1. 智能一键处理：同时进行标点修复、格式统一和样式清理。
2. 格式诊断：检查文档中的格式问题，不修改原文件。
3. 标点修复：修正常见中英文标点混用问题。
4. NBC 格式预设：按 NBC 文稿材料格式要求进行排版处理。
5. 预设编辑：三个内置模式可独立修改和恢复默认，也可新建、导入或导出自定义预设。
6. 标题控制：一级至多级标题可分别设置字体、字号和加粗。
7. 行距控制：支持单倍/多倍行距，也支持固定磅值行距。
8. 表格处理：支持表格宽度、行高、字体和对齐方式优化。
9. 批量处理：可一次选择多个 `.docx` 文件并输出到指定目录。

### Linux 使用说明

**安装版（推荐用于麒麟 V11 x86_64）**

从 v1.0.5 起提供 `.deb` 安装包；旧 Release 的 AppImage 不会自动获得本版改动。
下载 `NBC_DocFormat_linux_amd64.deb`，双击交给系统软件安装器安装，或在下载目录执行：

```bash
sudo apt install ./NBC_DocFormat_linux_amd64.deb
```

安装后从应用菜单打开 **NBC_DocFormat**，可固定到任务栏。程序和运行库安装在
`/opt/nbc-docformat`，不再每次启动解压到随机临时目录；日常运行不需要 `sudo`。
用户设置保存在 `~/.config/NBC_DocFormat`（设置了 `XDG_CONFIG_HOME` 时使用该目录），升级或卸载程序不会删除设置。
升级时安装新 `.deb` 即可；卸载执行 `sudo apt remove nbc-docformat`。
ARM64 使用 `NBC_DocFormat_linux_arm64.deb`。

安装版减少临时执行文件造成的重复识别，但不等于获得麒麟官方签名。
若系统提示“来源未认证”“未签名”或要求管理员批准，需要按该机器的安全策略信任此应用；
受管电脑由管理员审核。是否可长期免提示取决于麒麟版本和策略，不能由应用保证。
本项目不会更改系统安全策略。麒麟实机兼容性及授权行为仍需验证。

**便携版 AppImage**

先确认系统架构：

```bash
uname -m
```

选择对应 AppImage：

- 输出 `x86_64`：使用 `NBC_DocFormat_linux_amd64.AppImage`
- 输出 `aarch64` 或 `arm64`：使用 `NBC_DocFormat_linux_aarch64.AppImage`
- 输出 `loongarch64`：当前未提供预编译包，需要源码运行或单独构建

运行方式：

```bash
chmod +x NBC_DocFormat_linux_amd64.AppImage
./NBC_DocFormat_linux_amd64.AppImage
```

ARM64 用户将命令中的文件名替换为 `NBC_DocFormat_linux_aarch64.AppImage`。

银河麒麟、统信 UOS 等系统通常可直接运行对应架构的 AppImage。如遇 FUSE 相关错误，可安装系统的 `fuse` / `libfuse2` 包，或尝试：

```bash
./NBC_DocFormat_linux_amd64.AppImage --appimage-extract-and-run
```

## 使用方法

1. 点击输入区域选择一个或多个 `.docx` 文件。
2. 选择处理模式：智能一键处理、格式诊断或标点修复。
3. 选择格式预设，默认可使用 NBC 格式。
4. 如需调整，点击预设卡片上的“编辑”，修改后点击“保存设置”。
5. 点击开始处理，程序会在原文件旁生成新文件，或输出到指定目录。

原文件不会被覆盖。

### 编辑与恢复预设

- **GB/T 公文标准、学术论文、NBC格式**：在“智能一键处理”模式下，点击对应卡片的“编辑”，可修改字体、字号、行距、页边距、表格及页码等设置。
- **保存设置**：只影响当前编辑的模式，重启后仍生效；其他内置模式及自定义预设不受影响。
- **恢复默认**：点击“恢复此预设默认值”，再点击“保存设置”。
- **放弃修改**：关闭编辑窗口，在保存询问中选择“否”。
- **独立模板**：点击“自定义”可管理多份预设，支持新建、重命名、导入和导出。

## 格式识别与排版逻辑

软件先判断每个段落属于标题、正文、落款等哪一类，再应用所选预设中该类型的字体、字号、对齐、缩进和行距。当前实现采用固定规则，结合文字特征、位置和相邻段落进行判断；“智能一键处理”中的“智能”指这套自动处理流程，目前没有调用语言模型理解全文。

本节描述当前源码的实际行为，具体下载版本可能有所不同。识别规则主要位于 [scripts/formatter.py](scripts/formatter.py) 的 `detect_para_type()`，整体排版入口为 `format_document()`；格式诊断使用 [scripts/analyzer.py](scripts/analyzer.py) 中另一组检查规则。

### 1. 从输入文档到输出文档

“智能一键处理”的主要顺序是：

1. **修复标点和空格**：按所选空格处理方式及标点规则处理文字，生成中间 DOCX；后续识别看到的是这一阶段处理后的文本。
2. **读取有效预设**：使用 GB/T 公文标准、学术论文、NBC格式或当前自定义预设，并合并已保存的用户修改。
3. **执行可选预处理**：按配置进行强力清洗；若启用代码配置项 `split_heading_at_punct`，还会拆分部分“标题＋正文”混合段。内置预设默认关闭这两项。
4. **整理页面和上下文**：清理背景、设置页边距，预处理标题后与落款前的结构空行、附件分页，并建立非空段落序列。
5. **逐段分类和排版**：优先采用预扫描确定的附件正文标题，其余段落按下文规则判断；识别为日期后还可能统一日期写法。
6. **处理其他结构**：复查空行，处理表格、页码、脚注及中文换行规则，保存输出文件。

“格式诊断”只报告问题；“标点修复”处理标点、空格和相关字符字体，不执行上述完整的段落分类排版流程。

### 2. 软件用什么信息判断段落

| 信息 | 实际用途 |
|---|---|
| 段落文字 | 检查编号前缀、公文标题用语、日期形式、单位后缀、句末标点等 |
| 文字长度 | 决定是否进入短标题、主送机关、落款等规则；数字、标点和内部空格也计入长度 |
| 非空段落序号 | 判断是否位于前五个非空段落，以及文末约三分之一区域 |
| 实际段落序号 | 落款的“最后十段”判断仍使用包含空段的实际段落位置 |
| 上一个非空段落的识别结果 | 延续多行主标题或附件列表；中间的空段不会自动打断这种延续 |
| 前后段落文字 | 判断标题区是否结束、下一段是否像标题、后三个非空段落是否有日期 |
| 段落原有对齐属性 | 开头区域中，具有居中对齐属性的短段落可以作为主标题候选 |

这里的“段落”是 Word 文档中的段落结构，不等同于屏幕上显示的一行。自动折行通常仍在同一段；手动换行（如 Shift+Enter）通常也不会建立新段落。需要独立识别的标题和正文应分别成段。

常规分类主要遍历文档正文层的段落。表格单元格、脚注等结构有另外的处理流程，不会全部放进同一条标题层级识别链。原文的字号、加粗状态、Word“标题1／标题2”样式名称和自动编号属性，并未作为 `detect_para_type()` 的直接判断参数。

### 3. 规则的实际优先顺序

同一段可能同时符合多个特征，分类函数采用**按顺序判断、先命中先返回**的方式：

| 顺序 | 判断项目 | 说明 |
|---|---|---|
| 1 | 空文本 | 返回空段类型；主排版流程会单独处理无文字段落 |
| 2 | 主标题续行 | 上一段是主标题时，先检查当前段是否仍属于标题块 |
| 3 | 文末日期 | 对文末约三分之一范围内的日期优先识别 |
| 4 | 附件列表续项 | 上一段是附件时，优先识别紧随的数字编号条目 |
| 5 | 一级至四级标题 | 依次检查各类编号前缀 |
| 6 | 主送机关 | 检查冒号结尾的短段落，并排除正文提示词及部分标题上下文 |
| 7 | 附件标记或说明 | 检查“附件”“附件1”“附件：……”等形式 |
| 8 | 结束语 | 检查“特此通知。”“此致”等固定表达 |
| 9 | 一般日期 | 再检查日期，此处没有文末位置限制 |
| 10 | 落款单位 | 检查文末位置、单位后缀及后续日期 |
| 11 | 开头主标题 | 检查标题区域、标题文字特征和原有居中属性 |
| 12 | 正文 | 未命中前面规则的段落统一归为正文 |

独立“附件N”后面的附件正文标题，会在进入这套分类规则前由预扫描单独确定，详见附件规则。

### 4. 主标题和多行主标题

**首次识别主标题时**，通常要求当前段位于前五个非空段落之内，而且此前没有出现以下任一情况：

- 少于 50 个字符、以中文或英文冒号结尾的段落。
- 以“一、”“二、”等前缀开头的一级标题。

在这个开头区域内，未被更早规则识别的段落，满足下列任一条件便可成为主标题：

| 条件 | 例子或边界 |
|---|---|
| 匹配“关于……的通知／报告／请示／函／意见／决定／公告／通报／批复／说明／方案／总结／汇报／复函／答复／建议” | 如“关于开展年度检查的通知” |
| 以指定公文名称结尾，且该名称前有 2～30 个字符 | 如“年度重点工作方案”；结尾词还包括工作总结、实施方案、管理办法、暂行规定等 |
| 以指定机关或组织名称结尾，且该后缀前有 2～20 个中文字符 | 如“某某市人民政府办公室”；支持委员会、局、厅、院、部、委、中心、公司、集团、学校、大学等后缀 |
| 长度为 16～79 个字符，不以常见中英文句末标点结尾，也不以规则中的中文数字、阿拉伯数字或括号开头 | 用于补充没有典型公文名称的长标题 |
| 原有段落对齐属性为居中，且少于 60 个字符 | 如居中的短标题“工作安排” |

这些条件是候选规则，不会验证内容是否真的表达标题含义。尤其是“开头的较长文字没有标点”这条规则，也可能匹配到正文。

**上一非空段落已经是主标题时**，会优先执行“标题续行”规则。当前段少于 50 个字符，并同时满足以下条件，就继续归为主标题：

- 不以规则中的中文数字“一”至“十”、阿拉伯数字、左括号开头。
- 不以冒号结尾，不以“附件”开头，不匹配结束语或日期。
- 不以 `。！？.!?；;` 这些句末标点结尾。

例如“某某市人民政府办公室”“关于开展年度检查的”“通知”分成三个段落时，可以连续识别为主标题。**续行规则本身不再检查前五段限制**，也不要求原文居中；因此一段短正文如果没有明确标点，也可能被接入标题块。续行规则排除的标点范围比首次长标题规则窄，不能认为任意标点都能结束标题块。

### 5. 一级至四级标题

| 类型 | 可识别的文字前缀 | 长度条件 | 示例 |
|---|---|---|---|
| 一级标题 `heading1` | 中文数字“一”至“十”的组合，加顿号 `、` | 本条规则没有长度上限 | `一、总体要求`、`十一、其他事项` |
| 二级标题 `heading2` | 上述中文数字放在成对全角或半角括号中 | 本条规则没有长度上限 | `（一）工作目标`、`(二)职责分工` |
| 三级标题 `heading3` | 阿拉伯数字加半角点 `.`，可接空白；随后首个有效字符不能是数字或点 | 整段少于 60 个字符 | `1.工作安排`、`2. 检查内容` |
| 四级标题 `heading4` | 阿拉伯数字放在成对全角或半角括号中 | 整段少于 60 个字符 | `（1）人员分工`、`(2)时间安排` |

需要特别注意：

- `1.2.3 版本说明`、`1.2026年度计划`不会命中三级标题规则；`1. 2026年度计划`中点后的首个有效字符仍是数字，也不会命中。
- `1、工作安排`、`1．工作安排`中的顿号或全角点不在通用三级标题规则中。`1、`在附件列表上下文中可以另行识别为附件。
- 一级、二级标题没有整段长度限制，所以“一、总体要求。后面接着一大段正文”可能整段都应用标题格式。
- 三级、四级标题达到 60 个字符后，只是不再命中该级标题规则，仍会继续接受后面的规则判断；最终常见结果是正文。
- 识别主要看段首文字。只有 Word 自动编号、文字中没有实际编号字符时，不能依赖这套前缀规则稳定识别。
- 默认不会把同一段中的“标题部分”和“正文部分”自动拆开。若需要两种格式，建议在输入文档中先将二者分成独立段落。

### 6. 主送机关、结束语和落款

**主送机关 `recipient`** 的候选条件是：整段少于 30 个字符，以 `：` 或 `:` 结尾，冒号之前由中文、数字、顿号、逗号、括号和空白等允许字符组成。例如“各处室、直属单位：”。

程序会排除包含“现将、为了、根据、按照、经研究、为贯彻、为落实、为进一步、为深入、如下、以下、特此、兹将”等正文提示词，以及“的意见、的通知、的报告、的决定、的请示、的函”等片段的候选。因此“现将有关事项通知如下：”通常归为正文。

它还会查看下一个非空段落：如果下一段匹配部分“关于……的通知”等标题形式，或者长度为 16～79 个字符且不以指定中文标点结尾，当前段暂不认作主送机关，继续向后判断。这是为了兼容标题上下文，但也可能漏掉后面接无标点正文的真实主送机关。**主送机关规则本身没有限制必须位于文档开头。**

**结束语 `closing`** 通过固定表达匹配，包括：

- “特此说明／通知／报告／函复／函告／批复／公告／通报”，末尾可带中文句号。
- 单独的“此致”，以及“敬礼”“敬礼！”或“敬礼!”。
- “以上报告／意见／方案”后接最多 10 个字符，或“妥否”后接最多 10 个字符。
- “请”与“批示／审批／审议／指示／核准”之间最多 15 个字符，末尾可带中文句号。

这里没有另外要求结束语必须出现在文末；文字命中规则且未被前序规则截取，就可能归为结束语。

**落款单位 `signature`** 首先要求当前段位于文档实际段落的最后十段内，且少于 60 个字符。在此基础上按顺序判断：

1. 如果当前仍在前五个非空段落内，且此前没有出现冒号结尾的段落或一级标题，则暂停落款判断，保护开头的机关名称。
2. 若文字以单位后缀结尾，直接归为落款。后缀包括公司、局、委、部、厅、院、所、中心、办公室、集团、银行、学校、大学、医院、指挥部、领导小组、委员会、管理处、管委会。
3. 若文字以 `。！？.!?；;` 结尾，归为正文，避免完整正文句仅因附近存在日期而成为落款。
4. 否则检查后三个非空段落，任一段符合日期模式，就归为落款。

单位后缀只是文字匹配，不会验证它是否真是发文机关。靠近文末、没有句末标点的正文，如果以“公司”等词结尾，也可能误判。文档很短时，大多数段落都处于“最后十段”范围，前后文和标点的影响尤其明显。

### 7. 日期识别与日期文字统一

日期规则支持以下常见形式：

| 类别 | 示例 |
|---|---|
| 阿拉伯数字中文日期 | `2026年10月10日`、`2026年10月10`、`2026年10月` |
| 点、斜线或短横线分隔 | `2026.10.10`、`2026/10/10`、`2026-10-10`，以及相应的年月形式 |
| 中文数字日期 | `二〇二六年十月十日`、`二〇二六年十月`等符合当前正则的形式 |
| 占位日期 | `XXXX年XX月XX日`、`2026年XX月`等 |

匹配前会去除空白，将全角数字及部分分隔符转成半角，并尝试识别外层带一对全角或半角括号的日期。

“文末约三分之一”只限制前面的**优先日期判断**；后面的一般日期判断没有这个位置条件，因此一段独立日期在正文中间也可能归为日期。日期正则主要验证外形，**不会严格核验月份天数、闰年或日期是否真实有效**。

识别为日期后，一般的阿拉伯数字形式会转为中文年月日形式，例如 `2026.04.20` → `2026年4月20日`、`2026/04` → `2026年4月`。识别和转换是两套范围不同的规则：中文数字、占位符及带括号等形式可能能识别为日期，但保留原文字。

### 8. 附件说明、附件列表和附件正文标题

程序区分三种情况：

| 情况 | 判断和处理 |
|---|---|
| 附件说明 | 例如 `附件：1.人员名单`、`附件1：人员名单`，使用附件格式及相应悬挂缩进 |
| 连续附件列表 | 上一个非空段落是附件，当前以一至两位数字加半角点或顿号开头，并且编号后还有内容，例如 `2.预算明细`、`3、时间安排`，继续归为附件；这一步优先于三级标题判断 |
| 独立附件页标记 | 例如单独的 `附件`、`附件1`、`附件一：`。支持一至三位阿拉伯数字或由“一”至“十”组成的一至三个字符，末尾可带冒号；格式化时尽量使其另起一页，并检查已有分页，避免重复添加 |

对于独立附件页标记，程序还会预扫描其后第一个有效段落，跳过没有媒体的空段。候选文字不超过 80 个字符，不能是另一个附件标记，不能以指定标题编号或括号形式开头，也不能以 `。！？.!?；;：:` 结尾；满足这些条件后，原本居中或至少四个字符，就可被指定为**附件正文主标题**。

例如“附件1”后紧接“人员名单”时，“附件1”本身仍是附件标记，“人员名单”可按主标题排版。这个预扫描不受文档开头五段的限制，但条件也较宽：若附件没有独立标题，第一段短正文可能被当作标题。

### 9. 识别之后怎样套用格式

GB/T 公文标准、学术论文、NBC格式和自定义模式共用上述通用段落分类器。选择预设主要改变识别后的输出参数；它不会自动切换成另一套按文章语义识别章节的算法。某种类型在预设中没有专门配置时，会回退使用正文配置。

下表为**未做用户修改的 NBC 默认值**；字号单位为磅：

| 类型 | 中文字体 | 字号 | 加粗 | 对齐 | 首行缩进 | 行距 |
|---|---|---|---|---|---|---|
| 主标题 | 方正小标宋_GBK | 22 | 否 | 居中 | 0 | 1.0 倍 |
| 主送机关 | 方正黑体_GBK | 18 | 否 | 左对齐 | 0 | 1.23 倍 |
| 一级标题 | 方正黑体_GBK | 18 | 否 | 左对齐 | 36 磅，约两字符 | 1.23 倍 |
| 二级标题 | 方正楷体_GBK | 18 | 是 | 左对齐 | 36 磅，约两字符 | 1.23 倍 |
| 三级标题 | 方正仿宋_GBK | 18 | 是 | 左对齐 | 36 磅，约两字符 | 1.23 倍 |
| 四级标题 | 方正仿宋_GBK | 18 | 否 | 左对齐 | 36 磅，约两字符 | 1.23 倍 |
| 正文 | 方正仿宋_GBK | 18 | 否 | 两端对齐 | 36 磅，约两字符 | 1.23 倍 |
| 结束语 | 方正仿宋_GBK | 18 | 否 | 左对齐 | 36 磅，约两字符 | 1.23 倍 |
| 落款单位 | 方正仿宋_GBK | 18 | 否 | 右对齐 | 0 | 1.23 倍 |
| 日期 | 方正楷体_GBK | 18 | 是 | 居中 | 0 | 1.0 倍 |

这些类型的英文和数字字体默认设为 Times New Roman。中文引号按所在段落的中文字体处理；间隔号 `·` 单独按方正仿宋_GBK 处理。实际显示仍依赖打开文档的设备是否安装对应字体。

NBC 默认页边距为上 3.4 厘米，下、左、右各 2.8 厘米；页眉距离 1.5 厘米，页脚距离 1.75 厘米。表格默认使用 16 磅方正仿宋_GBK，脚注默认使用 12 磅方正仿宋_GBK。已保存的预设修改会覆盖相应默认参数。

此外还有一些独立处理：

- 默认的正文序列词加粗会处理“一是”“二要”“第一点”“第二条”等前缀；这不改变该段的正文分类。启用正文首句加粗时，以第一个中文句号为界。这类重建文字片段的操作会避开含媒体或特殊包装结构的段落。
- 标题块后、落款块前保留结构空行，普通空段会被压缩。表格前后也有独立空行处理，所以原文用大量空行撑出的版面不会原样保留。
- 含图片等媒体的无文字段落会另行处理行距，避免简单按空段压缩。
- 表格单元格主要使用表格配置。只有开启表格 `smart_align` 时，才根据表头、合计、序号列、数字、短文本等规则重新对齐；NBC 默认关闭该选项，保留单元格原有对齐。

“编辑／自定义”可以修改输出格式和部分处理开关，但目前没有提供修改“前五段”“少于六十字”等分类阈值的界面。修改字体字号也不会改变某段被识别成标题还是正文的规则。

### 10. 一份完整的识别示例

假设以下每一行都是 Word 中独立的一段，且没有其他前置内容：

```text
某某市人民政府办公室
关于开展年度检查的通知
各处室、直属单位：
现将年度检查有关事项通知如下。
一、总体要求
各单位应按要求完成准备工作。
（一）检查范围
检查内容包括人员管理和设备使用情况。
1.人员安排
（1）明确责任人
特此通知。
某某市人民政府办公室
2026.10.10
附件：1.人员名单
2.检查安排
```

对应的通用分类结果为：

| 段落 | 结果 | 主要原因 |
|---|---|---|
| 第 1 段机关名称 | 主标题 | 位于开头，匹配机关名称标题模式 |
| 第 2 段通知名称 | 主标题 | 紧接主标题，符合标题续行条件 |
| 第 3 段“各处室……” | 主送机关 | 短段落以冒号结尾，下一段是有句号的正文 |
| 第 4、6、8 段 | 正文 | 没有命中特殊类型规则 |
| 第 5 段“一、……” | 一级标题 | 中文数字加顿号 |
| 第 7 段“（一）……” | 二级标题 | 括号中的中文数字 |
| 第 9 段“1.……” | 三级标题 | 数字加半角点，长度符合条件 |
| 第 10 段“（1）……” | 四级标题 | 括号中的数字，长度符合条件 |
| 第 11 段“特此通知。” | 结束语 | 命中固定表达 |
| 第 12 段机关名称 | 落款单位 | 位于文末区域，且以“办公室”结尾 |
| 第 13 段日期 | 日期 | 命中文末日期规则；后续转为“2026年10月10日” |
| 第 14 段附件说明 | 附件 | 以“附件：”开头 |
| 第 15 段“2.检查安排” | 附件 | 上一段是附件，附件续项优先于三级标题 |

同一个机关名称在开头和结尾可以得到不同分类；同样的 `2.` 前缀在普通正文区和附件列表区也可以得到不同分类。这正是位置和上下文参与判断的结果。

### 11. 粘贴文本与 Markdown 的额外处理

“粘贴文本生成 docx”会先生成临时 DOCX，再进入同一套智能处理流程：

- **纯文本**：输入的文档标题单独建段，设置居中和初始字号；其中居中属性为后续分类提供标题线索，初始字号本身不参与分类判断。正文中的非空行会分别建段；单换行也会拆成段落，并非一定要有空行才能分段。
- **Markdown 判断**：根据特征累计分值。出现 `#` 至 `######` 标题加 3 分，至少两处 `**加粗**` 加 2 分，至少两条无序列表加 2 分，出现代码围栏加 2 分，出现以 `>` 开头的引用加 1 分；达到 3 分才走 Markdown 转换。
- **Markdown 标题转换**：第一个一级标题 `#` 用作主标题；`##` 转换成“一、”形式，`###` 转成“（一）”形式，`####` 至 `######` 转成“1.”形式。额外的 `#` 按一级分标题转换，已有的部分编号前缀会先清理以避免重复编号。
- **最终格式**：转换产生的文字和初始格式仍需经过段落识别和所选预设处理，因此原始 Markdown 中的局部加粗等效果不保证原样保留。当前转换不是完整的 Markdown 排版引擎。

### 12. “格式诊断”究竟检查什么

诊断模块没有逐段调用上述分类器，也没有逐项对照当前选中的预设检查标准符合性。当前主要检查：

| 检查项 | 当前触发逻辑 | 使用时应如何理解 |
|---|---|---|
| 标点 | 对含中文段落检查常见英文括号、引号、冒号、逗号、分号、问号、叹号及省略号、破折号等模式；`·` 的字体检查不要求段落含中文 | 是规则提示，具体语境仍需人工判断 |
| 编号 | 发现两种以上阿拉伯数字编号写法，如 `1.`、`1、`、`1）`、`（1）`，提示编号格式不统一 | 没有判断这些写法是否本来属于不同层级，所以合法多级编号也可能触发提示 |
| 首行缩进 | 对至少 10 个字符、未被排除的段落，检查首行缩进属性是否为空或零 | 居中段落以及“附件：”“联系人：”“抄送：”“主送：”等特殊行跳过；不会精确核验是否为两字符 |
| 行距 | 在上述参与段落检查的范围内，已设置的行距值出现一种以上，提示不统一 | 不会逐段核验是否符合预设要求；不同类型合法使用不同行距时也可能提示 |
| 字体 | 统计正文段落直接文字片段上明确设置的字体名，超过 4 种时提示过多 | 不等于完整解析所有中文字体槽及样式继承 |
| 字号 | 上述文字片段中明确设置的字号超过 4 种时提示不统一 | 不会检查某个标题是否恰好为规定字号 |

诊断主要遍历正文层段落及其直接文字片段，对表格、脚注和特殊包装内容没有完整覆盖。“未发现明显格式问题”表示没有触发这些检查条件，不代表整篇文档已通过所选模板或公文标准的完整校验。

### 13. 容易误判的情况与处理建议

| 现象 | 可能原因 | 建议 |
|---|---|---|
| 开头正文变成大标题 | 命中开头长文本、居中短文本或标题续行规则 | 检查正文是否独立成段、是否有正常句末标点，以及是否误设为居中 |
| 主标题没有识别出来 | 首次标题位置超出前五个非空段落，或此前已有冒号短句、一级标题 | 检查文前说明、文号等是否占用了识别区域；空段不计入前五段，但有文字的段落会计入 |
| 长段落整段变成标题 | 以“一、”或“（一）”开头，这两级没有长度上限 | 将标题和说明正文分段 |
| 数字小标题变成正文 | 长度达到 60 个字符，使用了不支持的点号，或点后内容以数字开头 | 检查实际编号文字，并将后接的说明正文分段 |
| 日期前正文被当作落款 | 处于文末、文字较短且缺少句末标点，或以单位后缀结尾 | 检查正文标点和段落划分；落款与正文分开 |
| 附件内容变成主标题或附件续项 | 附件标题预扫描或列表延续规则命中 | 检查是否使用独立“附件N”页标记，以及是否有明确的附件标题和正文结构 |
| 原来已有 Word 标题样式，但结果不符合预期 | 分类未直接读取标题样式名称或大纲级别 | 优先检查标题文字前缀、段落位置和上下文 |
| 文档看起来字体仍不对 | 识别或配置问题，也可能是设备缺少目标字体 | 分别核对段落分类、所选预设和本机字体安装情况 |

这些规则主要围绕常见中文公文结构设计。对于非标准编号、复杂封面、多篇材料合并、无标点提纲、论文专用章节等内容，建议先用代表性样本处理，再核对标题、落款、附件及正文的识别结果。

## 常见问题

**Win7/8 兼容版为什么还是打不开？**

请确认系统是 64 位 Windows，且 Windows 7 已安装 SP1。该兼容版使用 Python 3.8 和旧版 PyInstaller 构建，兼容性强于 Windows 10/11 版，但仍不支持 32 位系统。

**银河麒麟应该下载哪个 Linux 版本？**

在终端运行 `uname -m`。如果是 `x86_64`，下载 x86_64 版；如果是 `aarch64`，下载 ARM64 版；如果是 `loongarch64`，当前两个 AppImage 不能直接运行。

**为什么 Linux 上提示 Exec format error？**

通常是架构不匹配。请重新执行 `uname -m` 并下载对应架构的 AppImage。

**麒麟上打开“粘贴文本”或“自定义”，只有空白窗口怎么办？**

窗口外壳出现并不表示内部控件已创建完成。初始化中途异常、某一步阻塞，以及控件已创建但未正常显示，都可能表现为空白窗口。Windows 正常、麒麟异常，或终端没有报错，都不足以单独确定原因。

当前源码调整了弹窗初始化顺序，待控件创建且窗口可见后再抓取输入；这项修改针对一种可能的窗口时序问题，**尚未确认解决麒麟 V11 上反馈的白框问题**。新构建还会记录初始化阶段，即使没有异常输出，也可帮助定位执行停在哪里。

在包含这些改动的新构建中，打开这两个功能后，可查看 `~/.config/NBC_DocFormat/ui_diagnostics.log`；设置了 `XDG_CONFIG_HOME` 时，日志位于该目录下的 `NBC_DocFormat` 文件夹。Windows 位于 `%APPDATA%/NBC_DocFormat/`，macOS 位于 `~/Library/Application Support/NBC_DocFormat/`。日志达到约 1 MiB 时轮换，上一份为 `ui_diagnostics.log.1`。

日志包含 Python/Tcl/Tk 版本、窗口系统、初始化阶段、异常堆栈，以及窗口和主要控件的尺寸、可见状态；不会主动读取正文或设置表单的值。同步构造失败时会关闭本次创建的残留窗口，并显示错误及日志位置。Tk 的“可见”状态只能证明控件已映射，不能证明虚拟机屏幕上的像素已经正确绘制。

反馈时请附上本次打开功能对应的日志。旧版不会因本地源码已更新而自动获得这些诊断记录。

**为什么处理后的文档字体不一致？**

请确认系统安装了所需中文字体，例如仿宋_GB2312、方正仿宋、黑体、楷体_GB2312 等。缺少字体时，Word 或 WPS 可能会自动替换显示字体。

**可以处理 `.doc` 或 `.wps` 吗？**

Windows 版本可借助 Microsoft Office 或 WPS Office 转换后处理。macOS 和 Linux 请先手动另存为 `.docx`。
